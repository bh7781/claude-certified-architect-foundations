Hub-and-Spoke Orchestration

A coordinator sits at the centre of every multi-agent system the exam tests: it decomposes the topic, delegates to stateless subagents with fully explicit context, aggregates their results, and re-delegates gaps. Subagents research exactly what they're told and nothing more, so when a report comes back incomplete, the fault almost always traces to coordinator.decompose() — not to how hard any subagent worked.

TL;DR

If you remember nothing else

Every coverage gap traces back to decompose() — never to the subagents that researched exactly what they were assigned.
decompose(topic)→ delegate(subtopic, agent)→ completeness < 90%? yes→re-delegate gaps + partial (≤3 iterations) no→return the report
  1. All traffic goes through the hub. Subagents never talk to each other — every prompt, every result, every re-delegation passes through the coordinator, which is the only party with observability across the whole run.
  2. Subagents are stateless and isolated. A subagent has no memory of its own past calls and no access to the coordinator's history or another subagent's output unless the coordinator writes it into that call's prompt, explicitly, every time.
  3. Coverage gaps are a decomposition bug, not a research bug. If decompose() never produced "geothermal" as a subtopic, no subagent — however capable — can ever research it.
  4. More subagents cannot fix narrow decomposition. A third or fourth subagent still only gets whatever subtopics decompose() handed it; the fix is broader decomposition, not more spokes.
  5. Decomposition is two-phase, not one-shot. Phase 1 enumerates broadly; phase 2 hands the candidate list back to the model and asks it to self-check for missing categories (this build's phase 2 caught 10 categories phase 1 missed, including fusion and OTEC).
  1. Coverage has three buckets, not two. A subtopic with zero findings is a gap; one finding is partial (below MIN_FINDINGS_FOR_SUBSTANTIVE_COVERAGE); two or more is well_covered — only gaps and partials get re-delegated.
  2. Refinement is a loop with a cap. refine_coverage() keeps re-delegating gaps/partial subtopics until completeness clears 90% or the 3-iteration cap fires, whichever comes first.
  3. Isolation cuts both ways. Because subagents share no state, independent delegations have no cross-call dependency — research() fires all of them concurrently with asyncio.gather instead of awaiting one at a time.

Concept

Hub-mediated hand-off vs. direct peer messaging

The exam's one comparison for this topic: every "more efficient" alternative to routing through the coordinator is the wrong answer.

Hub-and-spoke exam default

  • The coordinator alone gets observability, consistent error handling, and controlled information flow — notes.md's three named reasons for centralisation.
  • Subagents never see each other's prompts or results unless the coordinator explicitly re-includes them (_summarize_existing_section, coordinator.py:289–315).
  • In this build: delegate_to_subagent() is the only function any subagent's output ever passes through on its way to becoming part of another prompt.

Direct subagent-to-subagent messaging always wrong on the exam

  • Sounds like an efficiency win — skip the round-trip through the hub — which is exactly the framing Exam Trap 3 is built to catch.
  • The exception worth memorising: current Claude Code lets a subagent spawn its own child subagents (nested parent-child delegation) — but that is still hub-mediated, top-down delegation, never a horizontal peer link. The exam's "never, for any reason" is about peer-to-peer messaging, and that stays wrong regardless.
  • Cross-reference: notes.md's "Current State" note under Hub-and-Spoke Architecture.

well_covered, partial, gaps = [], [], []
for subtopic in subtopics:
    count = finding_counts.get(subtopic, 0)
    if count == 0:
        gaps.append(subtopic)
    elif count < MIN_FINDINGS_FOR_SUBSTANTIVE_COVERAGE:
        partial.append(subtopic)
    else:
        well_covered.append(subtopic)

completeness = len(well_covered) / len(subtopics) if subtopics else 0.0
return {
    "well_covered": well_covered,
    "partial": partial,
    "gaps": gaps,
    "completeness": completeness,
}

while coverage["completeness"] < COMPLETENESS_THRESHOLD and iteration < MAX_REFINEMENT_ITERATIONS:
    iteration += 1
    targets = coverage["gaps"] + coverage["partial"]
    logger.info(
        f"Refinement iteration {iteration}: completeness "
        f"{coverage['completeness']:.0%} < {COMPLETENESS_THRESHOLD:.0%} threshold - "
        f"re-delegating {len(targets)} subtopic(s): {targets}"
    )

    redelegations = [
        self.delegate_to_subagent(
            self.subagents[i % len(self.subagents)],
            subtopic,
            topic,
            prior_findings=self._summarize_existing_section(subtopic, sections),
        )
        for i, subtopic in enumerate(targets)
    ]
    new_sections = list(await asyncio.gather(*redelegations))

Exam traps

Four traps, one distractor

Each card is a wrong answer the exam will offer you, why it fails, and what the correct answer looks like. Open them one at a time and try to recall the "why" before reading it.

Trap 1 · Blaming the subagent for a coverage gap
WrongConclude the web-search or doc-analysis subagent did a poor job when the final report misses an entire category, like geothermal or tidal energy.
WhyEach subagent only researches the subtopic(s) it was assigned (delegate_to_subagent, coordinator.py:182–243). If decompose() never produced that subtopic, no subagent ever saw it — Figure 1's "delegate" edge only ever carries what was decomposed.
RightTrace the gap to decompose()'s output first — verify_final_coverage (coordinator.py:415–450) does exactly this. Only blame delegation/context passing if the subtopic was assigned but its section still came back with zero findings.
Trap 2 · Assuming subagents share memory or inherit context
WrongExpect the doc-analysis subagent to "already know" what the web-search subagent found, or that a second call to the same subagent remembers the first.
WhySubagent isolation (Figure 2) means every prompt starts blank. The coordinator is the only thing holding sections[] across calls — nothing is shared automatically.
RightEvery fact a subagent needs — the subtopic, the goal, prior findings — must be written explicitly into that call's prompt (delegate_to_subagent, coordinator.py:199–217).
Trap 3 · Proposing direct subagent-to-subagent communication as an efficiency fix
WrongSuggest letting the web-search subagent hand its results straight to the doc-analysis subagent to save a round trip through the coordinator.
WhyDirect communication breaks the three things centralisation buys: observability, consistent error handling, controlled information flow (Figure 1's dashed "never" edge).
RightAll hand-offs stay coordinator-mediated, even when it costs an extra round trip. Efficiency never overrides the architecture on this exam.
Trap 4 · Adding more subagents to fix a narrow decomposition
WrongWhen renewable-energy coverage is missing geothermal, tidal, biomass and fusion, propose a third or fourth subagent to cover more ground.
WhyA new subagent still only gets whatever subtopics decompose() assigns it. More spokes on a hub with narrow output changes nothing.
RightFix decompose()'s breadth — the two-phase enumerate-then-validate pattern (coordinator.py:128–180) is built for exactly this, and Step 6's acceptance test exists to catch it if it regresses.
Distractor · The subagent just needed a better prompt or a stronger model
WrongSee the Step 5 demo's Nuclear Fusion Energy gap (0 findings on the first pass) and conclude the subagent's system prompt was too weak or the model too small.
WhyThe same subagent, same model, same system prompt returned 6 substantive findings the moment refine_coverage() re-delegated it with one extra sentence of context: "a previous attempt returned ZERO findings, try a different angle" (coordinator.log, iteration 1). Nothing about the subagent's capability changed.
RightThe fix that actually worked was re-delegation with better context, not a stronger subagent — this is the isolation principle at work, not a model-capability problem.

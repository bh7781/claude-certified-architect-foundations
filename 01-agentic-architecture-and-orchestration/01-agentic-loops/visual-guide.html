Agentic Loop Lifecycle

An agentic loop is deterministic control flow written in code. Every iteration sends the whole conversation to Claude, reads one field, stop_reason, and branches on it. That field is the only reliable termination signal. Everything else on this page hangs off that sentence.

TL;DR

If you remember nothing else

Branch on stop_reason. Nothing else is a termination signal.
user prompt→ messages[]→ messages.create(tools, messages)→ stop_reason ? tool_use→run the tool, append assistant turn + user tool_result, call again end_turn→find the text block, return its text, exit
  1. Two values, two actions. tool_use means run the tool and continue. end_turn means Claude is finished. Any other value means "not finished, check why", never "assume tool_use".
  2. The handoff is where loops break. On tool_use you append two messages: Claude's whole response as the assistant turn, then a user turn holding a tool_result whose tool_use_id equals the request's id. Skip the append and Claude never sees the result.
  3. Text and tool calls share one response. Claude often says "Let me look that up" and requests a tool in the same message. So content[0].type == "text" proves nothing, and neither does the phrase "I'm done".
  4. A cap is a safety net, never the control. MAX_ITERATIONS bounds runaway cost and logs a warning. It is not how the loop normally ends, and it is never the fix for an agent that stops too early.
  1. Do not force tool_choice: "any". It makes every response a tool call, so end_turn can never arrive and the loop runs until the cap fires.
  2. Claude picks the tool. Model-driven selection is the exam default because it adapts to unmapped cases. The one exception: deterministic compliance (financial, security, regulatory) is enforced in code, not left to the model. That is Task Statement 1.4.
  3. Tool definition = name, description, input_schema. The description is how Claude decides when to use it. Claude never runs your function; it returns a request and your loop dispatches by name.
  4. The history is the whole input. Every call resends the full messages list. There is no side memory, which is why the append matters and why input tokens grow each iteration.

The loop as control flow

One API call per iteration. The diamond is the only decision the code makes. The amber path returns into the message history, which is what makes this a loop rather than a single request.

Why the diamond is the whole exam. The questions test whether you branch on stop_reason or on something unreliable: the type of content[0], a phrase like "I'm done", or a loop counter. Only the field is deterministic and unambiguous.
Figure 2

How the message history grows

Step 3 is where loops break. Each tool_use iteration appends two messages: Claude's own turn, then a user turn carrying the tool_result. Forget the append and Claude never sees what the tool returned, so it has nothing new to act on.

The history is the whole input. Every iteration resends the full list. That is why the tool result must be appended: there is no side channel, no memory, nothing Claude can see except what is in messages. It is also why input tokens climb each iteration in the trace below.

Anatomy

What goes in, what comes back

Two objects carry the exam's vocabulary: the tool definition you register, and the Message the API returns.

Tool definition tools.py 79–96

{
  "name": "calculator",
  "description": "Evaluates a basic arithmetic expression (+, -, *, /, **) and returns the numeric result. Use this whenever the user asks for a calculation…",
  "input_schema": {
    "type": "object",
    "properties": {
      "expression": { "type": "string", "description": "A basic arithmetic expression, e.g. '12 * (3 + 4)'." }
    },
    "required": ["expression"]
  }
}
name
What Claude echoes back in tool_use.name. The loop uses it as a dictionary key to find the Python function.
description
How Claude decides when to use it. This text drives model-driven selection, so it says when, not only what.
input_schema
JSON Schema with type, properties, required. Claude's tool_use.input conforms to it.

Claude never runs calculator() itself. It returns a request; the loop dispatches it through TOOL_IMPLEMENTATIONS[name] and sends the result back.

stop_reason
The authoritative signal. Here it says continue, even though the first content block is plain text.
content[]
A list of blocks, and a single response can mix text and tool_use. This response is the premature-termination bug in one object.
id
Goes back verbatim as tool_use_id on the result.
Reference

Every stop_reason a loop can meet

The exam guide keys two values. The live API returns more, and a production loop handles them. The rule that covers all of them: anything other than end_turn means "not finished, check why", never "assume tool_use".

ValueScopeMeaningWhat the loop does
tool_useexamClaude wants one or more tools called.Run them, append results, call again.
end_turnexamClaude has finished its work.Extract the text block, return it, exit.
max_tokensproductionOutput hit the max_tokens limit; the reply is truncated.Raise the limit or continue the turn; do not treat as done.
pause_turnproductionA long-running server tool turn paused.Send the response back to let Claude continue.
stop_sequenceproductionA custom stop sequence you configured was hit.Read stop_sequence on the response and act on it.
refusalproductionThe model declined on an otherwise-normal 200 response.Surface it; do not loop hoping for a tool call.
model_context_window_exceededproductionThe response filled the model's context window.Handle like max_tokens truncation.

In this exercise the last five fall through to the "log a warning, stop" branch in Figure 1. That is the minimum a correct loop does with them: never confuse them with end_turn.

Concept

Who decides which tool runs

In the loop, Claude picks the tool from context. That is model-driven decision-making, and the exam favours it. There is one memorised exception.

Model-driven exam default

  • Claude reads the task, weighs the available tools, and chooses.
  • Adapts to situations the developer never mapped out.
  • Chains tools in orders nobody planned.
  • In this build: the prompt says "search, then calculate"; the code never says which tool runs when, and the run above chose search → calculator on its own.

Pre-configured decision trees, fixed sequences

  • The developer hard-codes which tool runs at which step.
  • Breaks on edge cases outside the mapped paths.
  • The exception worth memorising: when business logic demands deterministic compliance (financial operations, security checks, regulatory requirements), programmatic enforcement overrides the model's flexibility.
  • Covered in Task Statement 1.4, submodule 04, workflow enforcement and handoff.

Exam traps

Four traps and one distractor

Each card is a wrong answer the exam will offer you, why it fails, and what the correct answer looks like. Open them one at a time and try to recall the "why" before reading it.

Trap 1 · Using response.content[0].type == "text" to decide the loop is finished
WrongTreat a text block in position zero as "Claude is done" and return it to the user.
WhyClaude can return text alongside tool_use blocks in the same response. Text presence says nothing about completion. Iteration 1 in the trace above is exactly this shape: text first, then a web_search request, with stop_reason still tool_use.
RightBranch on stop_reason. Continue on tool_use, terminate on end_turn, regardless of which block types appear.
WorkedThe guide's support-agent bug: the agent works for simple queries but stops mid-task on complex ones. Claude says "Let me look up your order" and requests lookup_order; the code sees text at index zero, concludes it is done, and returns an incomplete answer. The fix is a stop_reason check, not a cap, not a retry.
Trap 2 · Setting "stop after 10 loops" as the primary stopping mechanism
WrongUse an iteration cap as the main way the agent terminates.
WhyIt either cuts off useful work (a task that genuinely needs 12 iterations) or runs unnecessary iterations (a task done in 3). The model already signals completion. The capped run above shows the cut-off case: the answer was one call away.
Rightstop_reason is the primary control. A cap is acceptable only as a safety net against runaway loops, placed as in the code above and logged as a warning.
Trap 3 · Parsing "I'm done" or "task complete" out of Claude's text
WrongScan the assistant text for a completion phrase and break the loop when you find one.
WhyNatural language is ambiguous. "I've finished analysing the first file" can precede more files. The stop_reason field exists precisely to remove that ambiguity.
RightNever inspect text for control flow. Read the field.
Trap 4 · Forcing tool_choice to "any" to stop the agent returning text
WrongSet tool_choice: {"type": "any"} so every response is a tool call.
WhyIt forces a tool call even when the agent is genuinely finished, so end_turn can never arrive and the loop runs forever. Then the safety cap fires, which is the wrong reason to stop.
RightLeave tool choice to the model and let it signal completion naturally through stop_reason.
Distractor · "Add an iteration cap" offered as the fix for premature termination
WrongThe agent stops early, so a plausible-looking answer proposes a cap or a retry count.
WhyCaps address runaway loops, the opposite failure. Premature exit means the loop is reading the wrong signal, and a cap changes nothing about that.
RightThe fix for premature termination is always to check stop_reason correctly. Reject cap-based answers to that question every time.
